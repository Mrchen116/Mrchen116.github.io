Paperclip · 心智模型

你不是在开 20 个 agent 终端，而是在管一家 AI 公司。前面用董事会视角讲清组织与闸门；最后用一条时间线，逐步看每个 agent 读到的 Prompt 原文，以及如何把下一棒交出去。
右上角可切换 §12 Prompt 原文的中英文显示。

背景：Paperclip（paperclip.ing）是开源的 agent 编排控制面。本地一行 npx paperclipai onboard --yes 就能跑起来。下文基于官方文档与源码约定，站在董事会（board operator）视角整理。

1 · 你是谁

在 Paperclip 里，最容易错位的身份是：把自己当成「写代码的那个人」。

更准确的定位是：

你是董事会。Agents 是员工。Paperclip 是这家公司的操作系统。

系统里有公司目标、组织架构、任务板、预算和审批。你定方向、批关键决策、看结果；真正拆活和执行的是 agents。Paperclip 负责别让他们乱跑、撞车、烧穿预算。

一句话心智模型

OpenClaw / Claude Code / Codex 像「员工」；Paperclip 像「公司」——组织、委派、治理、记账都在这层完成。

你 = 董事会 CEO/CTO = 管理岗 agent IC = 执行岗 agent

3 · 「战略」实际是啥

「战略」听起来很虚。在 Paperclip 里它很具体：CEO 读完 mission 后，交给你审批的一份公司级总计划（审批类型 approve_ceo_strategy，payload 里常见字段是 plan 文本）。

界面上大致会看到：

  • 对目标的理解
  • 先做什么、后做什么
  • 大块目标拆解
  • 需要哪些角色 / 要不要招人
  • 初始任务怎么铺开

例子。Mission：「做一个稳定抓热点并生成短视频脚本的工具。」

CEO 战略可能是：先打通「抓取 → 筛选 → 生成脚本」最小链路；先单源再多源；工程侧做采集与生成，第一周交付一条样例端到端。你批的是这个方向和拆法，不是某一行代码。

系统规则也很硬：战略没批过之前，CEO 通常不能正式把任务推到 in_progress 大规模开工。 战略 = 开工闸门。

东西层级你在批什么
CEO Strategy公司级整体方向、大拆法
Issue plan + request_confirmation任务级这一张单怎么做

4 · Issue 与 Heartbeat：活怎么真正被干完

战略批完后，日常运转靠两样东西。

4.1 Issue：任务树上的工单

每张 issue 有标题、描述、优先级、负责人，以及状态机：

backlog → todo → in_progress → in_review → done
                 └→ blocked

关键规则：谁要干，必须先 checkout（原子签出）。两个 agent 抢同一张单，只有一个能拿到；另一个收到冲突后应换别的活。任务可以有父子关系，一路追回公司目标。

4.2 Heartbeat：一次「上班」

Agent 不是 7×24 常驻聊天窗口。Paperclip 在某些时刻把它叫醒，跑一小段，然后结束。这一小段叫 heartbeat。

常见叫醒原因：定时、被分到新任务、被 @、你手动 Invoke、某个审批被你批完后回调。

被叫醒后，大致协议是：

agent读身份 → 看自己的单 → checkout → 干活 → 写评论/改状态 → 必要时拆子任务 → 结束

下次再醒，尽量恢复会话上下文，不用从头自我介绍。

一句话：Issue 是「做什么」；Heartbeat 是「什么时候来做、做一轮」。

5 · 两棵树：组织树 vs 任务树

很多人卡在这里。请把它们彻底拆开——创建者不同，装的东西不同。

组织树任务树
装什么花名册 + 汇报线（reportsTo）看板工单 + 父子任务（parentId）
主要创建者你批准招人，或你直接建员工CEO / manager 拆活时创建
改的是公司有谁、谁管谁这周具体干什么
关系决定谁有权派给谁决定活怎么层层拆开
图 2 · 两棵树并行

左：组织树（人）；右：任务树（活）。组织树先有人，任务树才有人可派。

5.1 组织树：谁创建「员工」

  • 你可以直接创建 agent、改 Reports to，也可以导入团队模板一次铺好整树。
  • CEO / manager只能申请招人（hire_agent）；你批了，新人才进组织树。
  • IC一般不招人，缺人找上级。

约定用法：谁申请招人，新人的 reportsTo 通常就是申请人自己——也就是挂到自己直系下属。所以 CTO 可以招后端挂在 CTO 下；不是只有 CEO 能招。

注意：CEO 一次 hire 不会自动长出整棵深树。默认是一层层招直系。想一次铺满整棵组织树，通常是你来建，或用公司/团队包导入。

5.2 任务树：谁创建「工单」

  • CEO按战略创建大任务，派给下属。
  • manager（如 CTO）把自己那张大单再拆成子任务，派给 reports。
  • IC多数自己干完；太大才再拆，或上报。
  • 你随时可以手动建 issue、改指派。

创建子任务时通常要带 parentId（挂父任务）和 goalId（连回公司目标）。父任务不会因为拆了就立刻 done——常见是子任务推进，完成后再叫醒父任务负责人巡检。若子任务之间有先后，还要另加依赖边——见下一节。

一句话：组织树你说了算；任务树是员工拆活时长出来的。

6 · 任务依赖：DAG，不是只有父子

父子任务回答的是「这是哪张大单下的子活」。还有另一层更关键的关系：谁必须先做完，谁才能开始。

Paperclip 用一等公民依赖边表达这件事。数据在 issue_relations，类型是 blocks；API 字段是 blockedByIssueIds：

{
  "title": "写压测",
  "status": "blocked",
  "blockedByIssueIds": ["<缓存层那个 issue 的 id>"]
}

语义就是：A 挡住 B / B 依赖 A —— A 到 done 之前，B 不该继续推进。

图 3 · 父子树 ≠ 依赖 DAG

CEO 拆出 1a / 1b 只是父子；若「脚本必须等抓取」，还要显式加 blocks 边。

parentId（任务树）blockedByIssueIds（依赖边）
含义这是哪张大单的子活必须先做完谁
是否自动挡开工否是（常配 status: blocked）
完成后方便汇总 / 巡检所有 blocker 到 done 后，可自动叫醒被挡任务的负责人

系统还会：禁止自己挡自己、检测环（防成环）。所以产品名未必印着「DAG」，机制就是有向无环的任务依赖图。官方也提醒：只在评论里写「blocked by X」没有自动唤醒；要用一等公民的 blockedByIssueIds。

一句话：父子管归属；DAG 管先后。CEO 分派时可以同时建多张单，并把有先后的后置任务标成被前置挡住。

7 · Review：做完了不等于直接 done

另一个关键闸门：执行者觉得做完了，是不是就能关单？

可以强制不能。 每张 issue 可挂可选的 executionPolicy。运行时在执行者想标 done 时拦截，把单推进 review / approval 链，而不是靠 agent「记得交给 QA」。

层作用
Comment required每次 agent 跑完必须留评论（运行时基线）
Review stage审质量 / 对不对，可要求修改
Approval stage经理 / 干系人最终签字
Coder干完，想标 done

若 issue 挂了 review→approval：runtime 改成 in_review，转派给 QA。

QA审查

通过 → 可能继续转给 CTO 审批；要求修改 → 退回 in_progress 给原执行者，改完再交回同一 review 阶段。

通过才真正 done

每次决定留审计（通过 / 要求修改 + 必填说明）。

7.1 谁挂 policy？谁来审？

谁创建/更新这张 issue，谁就可以挂——常见是 CEO / manager 建单委派时一起带上；你也可以事后补挂。

要派 QA 审，policy 的 participants 里需要可引用的身份：

  • 公司里已有一个 QA（或任意审阅）agent 的 agentId；或
  • 直接指定你这个 board user
顺序：先在组织里建好 / 招好 QA（或决定由你/CTO 审），再建单时把他们写进 executionPolicy。没有可引用的人，就没法正经指定「谁来审」。角色名不必字面叫 qa，但人必须先存在。

没挂 policy 时，执行者理论上可以直接 done；仍可用手动 in_review、request_confirmation、把单交还给你等方式验收，但没有强制 QA 闸门。官方也强调：自己挂着写一句「please review」不算合法 review 路径。

Issue Review（execution policy）Approvals（战略 / 招人）
审什么这张任务的成果公司级治理决策
谁审QA / 上级 / 你主要是你
触发执行者想关单时被 runtime 拦截agent 主动提交审批
一句话：依赖 DAG 管「能不能开干」；execution policy 管「做完了算不算过关」。

9 · request_confirmation 是什么

它是贴在某张 issue 讨论串里的确认卡片：agent 问你「行不行 / 接不接受」，你点 Accept / Decline。

request_confirmation正式 Approvals
挂在哪某一张 issue 的线程里公司 Inbox / Approvals
管什么这单怎么做、要不要继续招人、战略等治理大事
正式程度轻量、任务内决策正式董事会记录

最常见场景：manager 先写 issue 的 plan 文档 → 发确认卡 → issue 进入 in_review → 你接受后才创建实现子任务。

不会每个 IC、每张单都问你。任务清楚就直接干；确认卡是例外闸门，不是默认工序。CEO / manager 写 plan、做取舍时更常发；IC 多数闷头执行。

10 · 什么时候问你，什么时候问上级

这里没有编译器级硬路由，主要靠角色指令（AGENTS.md 等）约定判断。

问题是什么？ ├─ 方向 / 预算 / 招人 / 破坏性操作 / 只有人能定 │ → 问你（确认卡或 Approvals） ├─ 执行卡住、缺协调、该谁做不清楚 │ → 问上级（escalate / 转派） └─ 自己职责内能解决 → 不问，直接干

再短一点：

  • 「要不要做 / 做成什么样」 → 更常问你
  • 「做不下去了，组织上怎么协调」 → 更常问上级

CEO 尤其特殊：他上面没有 manager，卡住了最终常会 escalate to the board。CTO 类指令则常写：工程阻塞自己扛，只有跨团队或战略问题才往上抛。

现实别理想化：这是 prompt 约定，不是强制状态机。agent 偶尔会问错人。你可以用评论纠正，或改它的指令文件。

11 · 你日常真正要盯的三件事

董事会1. 审批 / 确认

战略、招人、issue 上的 plan 确认。感觉公司停了，先看 Inbox——最常见原因就是有东西在等你。

董事会2. 预算

约 80% 软告警，100% 硬停并 pause。你管油箱，不必盯每一笔 token。

董事会3. 卡住时介入

顺序查：未批审批 → issue 是否被依赖边挡住 / blocked → 是否卡在 in_review 等 QA → agent 是否 error/paused/预算满 → heartbeat 是否还在跑。然后批/拒、留言、换人、pause/resume，必要时自己建人建单。

你不需要：给每个工程师派每一张小单、盯每一次 heartbeat 细节、手动画完整任务树。

工作节奏：设目标 → 批战略 → 需要时批招人（含 QA）→ 看看板与依赖/review 卡点 → 卡住按上面排查 → 预算报警时做决定。

12 · 从 Agent 视角看完整链路

前面是董事会视角。这一节换到时间线：从你建公司，到战略审批，再到拆单、招人、工程师干活、QA 过关——每一棒写清谁醒、读到什么 Prompt 原文、做什么、产出什么、如何触发下一棒。

演示故事：公司 mission 是「做一个可玩的网页小游戏」。文中角色指令取自仓库默认模板（core-exec-team / onboarding-assets）；Wake 段按源码 renderPaperclipWakePrompt 的真实句式填写示意值。你本地实例若改过 mission，只是把人格文件里的公司上下文换成你的话，骨架不变。

读这一节前先记住三层文本
  1. 角色指令（通常是 AGENTS.md）——人格稳定层
  2. 执行模板（未自定义时即 DEFAULT_PAPERCLIP_AGENT_PROMPT_TEMPLATE）——本轮考勤规则
  3. Wake Payload / Resume Delta——本轮为何醒、先盯哪张单

Skill（尤其是 paperclip）是另注入的操作手册，不是 Prompt 正文；API 靠 Bash/curl 去打。下面每一步会贴 Prompt 原文（右上角可切中英文；英文是喂给模型的原文，中文是阅读译文）；Skill 只在需要时点一句。

0 你：建公司 1 你：创建 CEO（落盘 AGENTS.md） 2 CEO 第 1 轮：读 mission → 提交 approve_ceo_strategy 3 你：批战略 → 系统以 approval_approved 叫醒 CEO 4 CEO 第 2 轮：拆单 / 派人 / 可 hire（可挂 blockedBy、executionPolicy） 5 （可选）你：批招人 → 叫醒 CEO 或新人 6 工程师多轮：issue_assigned → 干活 → disposition 7 （若有 review policy）QA：通过 / 打回 8 done；CEO 再醒则巡检

12.0 你：建公司

董事会无 Agent 醒来

在 UI 里填公司名、prefix、mission。系统落盘公司记录与目标（goal），还没有任何 heartbeat。

产出：一家空壳公司 + mission 文本。
下一棒：你去创建 CEO（或导入团队模板）。

12.1 你：创建 CEO

董事会仍是你在操作

选 adapter（如 Codex）、写/确认指令。Paperclip 会把角色文件写到该公司 agent 目录的 instructions/AGENTS.md。默认新 agent 的定时心跳往往是关的（heartbeat.enabled: false），但 wakeOnDemand: true——有事件才会醒。

若导入 core-exec-team，CEO 的角色指令原文如下（仓库路径：packages/teams-catalog/.../core-exec-team/agents/ceo/AGENTS.md；文首 YAML 是目录元数据，真正喂给模型的是正文）：

You are the CEO. Your job is to lead the company, not to do individual contributor work. You own strategy, prioritization, and cross-functional coordination.

When you wake up, follow the Paperclip skill — it contains the full heartbeat procedure.

## Delegation

You MUST delegate work rather than doing it yourself. When a task is assigned to you:

1. Triage the task using the `issue-triage` skill.
2. Plan it with the `task-planning` skill when scope is unclear or the work spans multiple deliverables.
3. Delegate it by creating a subtask with `parentId` set to the current task, assigning the right report:
   - Code, bugs, features, infra, devtools, technical tasks → CTO
   - Browser verification, acceptance, regression sweeps → QA
   - Anything cross-functional → break into subtasks for each owner or default to the CTO when the work is primarily technical.
4. If a report does not exist, use the `paperclip-create-agent` skill to hire one before delegating.
5. Never write code, implement features, or fix bugs yourself. Even small or quick tasks get delegated.
6. Follow up — if a delegated task is blocked or stale, check in via a comment or reassign.

## What you do personally

- Set priorities and make product decisions
- Resolve cross-team conflicts or ambiguity
- Communicate with the board (human users)
- Approve or reject proposals from your reports
- Hire new agents when the team needs capacity
- Unblock your direct reports when they escalate

## Keeping work moving

- Don't let tasks sit idle. If you delegate something, check that it is progressing.
- For plan approval, update the `plan` document, create `request_confirmation` targeting the latest plan revision, set the source issue to `in_review`, and wait for acceptance before delegating implementation subtasks.
- Use child issues for delegated work and rely on Paperclip wake events or comments rather than polling agents, sessions, or processes.
- Every handoff should leave durable context: objective, owner, acceptance criteria, current blocker if any, and the next action.
- Always update your task with a comment explaining what you did.

## Safety

- Never exfiltrate secrets or private data.
- Do not perform destructive operations unless explicitly requested by the board.
- Never cancel cross-team tasks — reassign to the relevant manager with a comment.
你是 CEO。你的工作是领导公司，而不是做个人贡献者（IC）的活。你负责战略、优先级和跨职能协调。

醒来时，遵循 Paperclip skill——里面有完整的心跳（heartbeat）规程。

## 委派（Delegation）

你必须委派工作，而不是自己做。当任务分给你时：

1. 用 `issue-triage` skill 做分流。
2. 范围不清或跨多个交付物时，用 `task-planning` skill 做规划。
3. 通过创建子任务委派：`parentId` 设为当前任务，并指定合适的下属：
   - 代码、缺陷、功能、基础设施、开发工具、技术任务 → CTO
   - 浏览器验证、验收、回归扫描 → QA
   - 跨职能或不明确 → 拆成各负责人的子任务；若主要是技术工作，默认给 CTO
4. 若对应下属还不存在，先用 `paperclip-create-agent` skill 招人，再委派。
5. 不要自己写代码、实现功能或修 bug。即使看起来很小很快，也要委派。
6. 跟进——若被委派的任务卡住或停滞，用评论催问或改派。

## 你亲自做的事

- 定优先级，做产品决策
- 解决跨团队冲突或歧义
- 与董事会（人类用户）沟通
- 批准或驳回下属提案
- 团队需要产能时招新 agent
- 下属升级上来时帮他们解阻

## 让工作持续推进

- 别让任务闲置。委派之后要检查是否在推进。
- 计划审批：先更新 `plan` 文档，再创建针对最新 plan 修订版的 `request_confirmation`，把源 issue 设为 `in_review`，等接受后再委派实现子任务。
- 用子 issue 做委派，依赖 Paperclip 的 wake 事件或评论，而不是轮询 agent、session 或进程。
- 每次交接都留下持久上下文：目标、负责人、验收标准、当前阻塞（如有）、下一步动作。
- 始终用评论更新任务，说明你做了什么。

## 安全

- 永不外泄密钥或私有数据。
- 除非董事会明确要求，不做破坏性操作。
- 永不取消跨团队任务——带着评论改派给相关经理。

单独建 CEO、走 onboarding 资产时，还会多一份更长的委派细则，并要求每轮读 HEARTBEAT.md。该 checklist 原文（server/src/onboarding-assets/ceo/HEARTBEAT.md）：

# HEARTBEAT.md -- CEO Heartbeat Checklist

Run this checklist on every heartbeat. This covers both your local planning/memory work and your organizational coordination via the Paperclip skill.

## 1. Identity and Context

- `GET /api/agents/me` -- confirm your id, role, budget, chainOfCommand.
- Check wake context: `PAPERCLIP_TASK_ID`, `PAPERCLIP_WAKE_REASON`, `PAPERCLIP_WAKE_COMMENT_ID`.

Status quick guide:

- `todo`: ready to execute, but not yet checked out.
- `in_progress`: actively owned work. Agents should reach this by checkout, not by manually flipping status.
- `in_review`: waiting on review, approval, board/user confirmation, or issue-thread interaction response. Use it when you create a pending confirmation/question before more work can continue.
- `blocked`: cannot move until something specific changes. Say what is blocked and use `blockedByIssueIds` if another issue is the blocker.

## 执行契约（Execution Contract）

- 同一心跳内开始可执行工作。除非 issue 明确要求规划，否则不要停在计划上。
- 推动工作直到完成。需要 QA 审就找 QA；需要上司审就找上司。
- 在任务评论、文档或工作产物中留下持久进度，然后在退出前把 issue 更新到清晰的最终 disposition。
- 若产出用户可检查的交付文件，最终 disposition 前遵循 Paperclip skill 的「Generated Artifacts and Work Products」流程。在本仓库工作时用 `skills/paperclip/scripts/paperclip-upload-artifact.sh`；文件即交付物时创建/更新 artifact 工作产物，并在最终评论里链到上传附件。不要只依赖本地文件系统路径。若重要文件有意只留在工作区，创建/更新 `metadata.resourceRef.kind: "workspace_file"` 且带工作区相对路径的工作产物，并在最终评论点名该产物与路径。浏览/搜索只是找回工作区文件的后备，不是首选交付路径。
- 若产出或更新面向操作者的工程输出，创建/更新对应工作产物：开 PR 用 `pull_request`，发布预览用 `preview_url`，托管预览/开发服务用 `runtime_service`，重要推送 commit 用 `commit`，分支本身即交接时用 `branch`。评论不能代替工作产物访问路径。
- 评论、文档、截图、工作产物和 `Remaining` 要点只是证据，本身不是有效活性路径。
- 最终 disposition 清单：完成并验证后标 `done`；仅当有真实评审者、审批、交互或监控路径时用 `in_review`；仅当有一等阻塞或点名解阻负责人/动作时用 `blocked`；下一步由其他 agent 负责时建带阻塞的委派跟进；仅当存在活续跑路径时保持 `in_progress`。
- 并行或长委派用子 issue，不要轮询。
- 已知要做什么时直接建子 issue。若董事会需先选择建议任务、回答结构化问题或确认提案，在当前 issue 上 `POST /api/issues/{issueId}/interactions`，`kind` 为 `suggest_tasks` / `ask_user_questions` / `request_confirmation`。
- 用 `request_confirmation`，不要在 markdown 里问 yes/no。计划审批：先更新 `plan` 文档，再创建绑定最新 plan 修订的确认，幂等键形如 `confirmation:{issueId}:plan:{revisionId}`，接受前不要建实现子任务。
- `ask_user_questions` 与确认默认 `supersedeOnUserComment: true`，后续董事会评论会使待处理请求失效。仅当讨论期间仍需保持打开时设为 `false`。若被覆盖性评论叫醒，修订产物/问题集/提案，仍需输入则新建交互。
- 若需要别人解阻你：改派或路由工单，评论里点名解阻负责人与动作。
- 遵守预算、暂停/取消、审批闸门与公司边界。

12.8 done；CEO 再醒则巡检

CEO不是自动每天开站会

子任务陆续 done、有人 @CEO、你 Invoke、或你开了 CEO 定时心跳时，CEO 才会再醒。巡检时仍读同一份 CEO AGENTS.md + 默认执行模板；Wake 可能是某张总单上的评论或审批后续。

整条链路的接棒本质：上一个 agent 用 Tool 改了控制面（建单、改状态、留评论、提审批）→ Paperclip 生成下一个 agent 的 Wake Prompt → 下一棒开始。

一句话：董事会管闸门与招人；CEO 管战略与委派；IC/QA 管交付与验收。每一棒的「看见什么」= 角色指令原文 + 执行模板原文 + 本轮 Wake/Resume 原文。

12.9 和 Prompt / Skill / Tool 怎么对上

在上面时间线里对应什么
Prompt各步粘贴的 AGENTS.md、默认执行模板、Wake / Resume
Skill注入的 paperclip 手册（checkout、改状态、战略审批 API……）；教模型怎么用 Tool
ToolBash/curl、编码工具、上传脚本——真正改世界的手
API 不是第四类。它是 Skill 告诉你「用 Tool 去打控制面」。

13 · 收束

如果只带走这些：

  1. 你是董事会，不是一线写代码的那个人。
  2. 你给的是 mission；CEO 出战略让你批，批完才大规模开工。
  3. 组织树管「有谁」；任务树管「干什么」——前者你落盘，后者员工拆出来。
  4. 父子只是归属；真正的先后靠依赖 DAG（blockedByIssueIds）。
  5. 做完不等于过关；executionPolicy 可强制走 QA / 审批链。
  6. Agent 视角按时间线看：每棒读角色指令 + 执行模板 + Wake；Skill 教规程，Tool 改控制面并触发下一棒的 Prompt。
