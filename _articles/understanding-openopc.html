OpenOPC · AI-Native Company

OpenOPC 的重点不是“同时启动多个 Agent”，而是把组织、人员、工作流和经验拆成可持续运转的系统。本文用一项落地页任务，讲清 Self-Built、Self-Run、Self-Grown 如何形成闭环。

项目定位：OpenOPC 是一个开源的 AI 原生公司运行时。它同时提供浏览器 Office UI 和 CLI；底层 Agent 内核是项目自研的 Native Runtime，模型接入由 LiteLLM 负责，也可以把 Codex、Claude Code、Cursor、OpenCode 等外部 Agent 当作可选执行后端。

1 · 它解决的不是“多 Agent”，而是“组织如何运转”

一个多 Agent demo 往往是这样的：开几个不同 prompt 的 Agent，让它们并行回答，最后找一个 Agent 汇总。对短任务够用，但一旦任务变长，很快会碰到组织问题：

  • 到底需要哪些岗位？岗位和具体执行者有什么区别？
  • 谁能把任务派给谁？跨层级委派是否允许？
  • 一个子任务完成后，谁来审，审稿发生在哪个上下文？
  • 上游没完成，下游如何等待；同级任务如何并行？
  • 执行中卡住了，是问同事、找经理，还是找人类？
  • 这次做对的事，下一次如何被复用？

OpenOPC 把这些问题归纳成三个紧密耦合的机制：

图 1 · OpenOPC 的三个闭环阶段

红：组织搭建；紫：运行时协作；绿：经验沉淀；赭黄：学习结果回流到下一次组队。

Self-Built 决定“公司里有哪些座位、谁来坐”；Self-Run 决定“活怎么流动”；Self-Grown 决定“干完以后谁变强、知识留下多少”。

2 · 先分清三个词：Role、Talent、Employee

理解 OpenOPC 的第一道门槛，是不要把岗位和人混为一谈。

概念回答的问题例子
Role公司需要什么岗位；职责、汇报线、权限和工具是什么Designer、Frontend Engineer
Talent Template人才市场上有哪些候选人蓝图React Specialist、Conversion Copywriter
Employee这次具体是谁坐在岗位上；其个人经验是什么Alice、frontend-landing-expert

Role 是座位，不是人

Role 定义组织结构：向谁汇报、能委派给谁、可以使用哪些工具。它相对稳定。今天的 Designer 可以是 Alice，下次也可以换成另一位员工。

结构职责权限汇报关系

Employee 是坐在座位上的具体人

Employee 有唯一身份、来源模板和历史经验。同一个 Role 由不同 Employee 担任，执行结果会不同：老员工带着过去的经验，新员工主要带着模板人设和共享 Playbook。

经验分已学技能动态画像

为什么一定要拆开？因为岗位需要稳定，人员需要流动；岗位规定权责，人员积累经验。如果二者绑死，系统就无法在保留组织结构的同时换人，也无法准确回答“这次究竟是谁做得好”。

3 · Self-Built：开工前先把班子搭好

Self-Built 是执行前的 staffing 阶段。当前实现从用户选定的组织架构开始：可以是内置的 corporate 架构，也可以是保存下来的自定义组织。组织架构里是一组 Role 及其 reports_to 汇报关系。

一个容易被文案带偏的地方：“Self-Built 自动搭组织”不等于每次请求都让 LLM 从空白生成一棵任意组织树。当前主要路径是加载选定架构，再针对本次目标为现有 Role 做 staffing；用户也可以编辑、保存和导入组织架构。

3.1 招聘器比较两类人

每个 Role 会形成一条招聘需求。招聘器先判断这个岗位是否值得专门筛选人才；如果需要，就同时看：

  • Existing Employee Pool：组织里已有的员工，带经验分、已学技能和历史表现；
  • Talent Template Pool：本地或导入的人才模板，代表可以新招的专业人选。

每个 Role 最终会落到四种决策之一：

决策含义
existing_staff复用有经验的现有员工
proposed_hire从人才模板中招聘新员工
direct_role_execution不需要专门选人，按岗位默认能力执行
fallback_role_only没有可信候选人，退回岗位基础执行

3.2 一份落地页任务会怎样组队

假设用户提出：

为“AI 记账助手”制作一个营销落地页，需要文案、视觉设计、前端实现和质量把关。

组织架构里有 PM、Designer、Frontend Engineer、Copywriter 和 Reviewer。招聘器可能做出如下决定：

RoleStaffing理由
PM直接角色执行通用协调岗位，无需专门招聘
Designer复用 AliceAlice 有落地页经验和相关技能
Frontend Engineer招聘 React Specialist现有前端员工的经验与任务不匹配
Copywriter招聘 Conversion Copywriter组织里没有现成的转化文案员工

用户确认招聘提案后，Talent Template 才会被实例化为 Employee。最终形成一份 Staffing Override——本次运行中 Role 到 Employee 的具体映射。

Designer → alice-001 Frontend Engineer → frontend-landing-expert Copywriter → copywriter-conversion

4 · Self-Run：任务树不是预先画好，而是在运行中长出来

Self-Run 是 OpenOPC 最核心的部分。它不只是并行调用几次模型，而是围绕 Work Item 运转。

Work Item（工作项） 是公司模式下真正的业务任务单元，可以理解为看板上的一张卡。它记录要做什么、由哪个 Role/Seat 持有、当前 Phase、依赖哪些上游、需要通过什么 Gate。

4.1 Projection 只是组织脚手架

运行开始前，系统会根据组织拓扑生成一份 runtime plan。这里的 Projection（任务投影） 描述每个座位是 manager 还是 executor、默认审稿规则、可以委派给谁。

但它不是本次任务的完整任务树。启动时只创建根 Work Item；这次到底拆几块、兄弟任务谁依赖谁，由每一层 manager 在自己的 dispatch turn 中动态决定。

结论：组织结构预先存在，业务任务树运行时生长。PM 只拆自己的下一层；如果下属也是 manager，它再继续拆下一层。

4.2 Dispatch turn 调用什么工具

经理拿到需要向下拆解的 Work Item 时，会进入 dispatch turn，调用公司协作工具 delegate_work。这个调用会声明：

  • 子任务的标题、目标和交付物；
  • 分给哪个直属下级 Role；
  • 兄弟子任务之间的 depends_on；
  • 必要的审稿和协作约束。
delegate_work(
  children=[
    { role: "copywriter", title: "撰写落地页文案" },
    { role: "designer", title: "设计视觉稿",
      depends_on: ["copywriting"] },
    { role: "frontend_engineer", title: "实现页面",
      depends_on: ["design"] }
  ]
)

调用成功后，系统创建子 Work Item，把业务依赖写入 Dependency DAG（依赖有向无环图），然后让父 Work Item 进入 WAITING_FOR_CHILDREN。

委派边界：正常运行路径下，delegate_work 面向组织拓扑允许的下游角色，当前文档化的默认模型是直属下级。PM 不替下属的团队继续拆第三层；下属 manager 收到自己的卡后，在自己的 dispatch turn 中继续拆。

4.3 Phase 是唯一权威状态

每张 Work Item 由一个 Phase（阶段）描述当前业务状态。看板列、当前负责人和是否可调度，都是从 Phase 推导出来的。

阶段组典型 Phase含义
TodoREADY / WAITING_DEPENDENCIES可调度，或等待上游
In progressRUNNING / WAITING_FOR_PEER / WAITING_FOR_CHILDREN执行中，或等待同事/子任务
ReviewAWAITING_MANAGER_REVIEW / AWAITING_HUMAN等经理或人类判断
TerminalAPPROVED / FAILED / CANCELLED完成、失败或取消

调度器持续刷新 DAG：没有依赖的卡可以并行进入 READY；上游未通过时，下游保持等待；上游 APPROVED 后，下游才进入可执行状态。

5 · 最关键的细节：PM 等孩子时，到底在哪个上下文工作

当 PM 用 delegate_work 派出子任务后，它的父 Work Item 进入 WAITING_FOR_CHILDREN。这很容易造成一个误会：

是不是只有所有子任务做完，系统才给 PM 发消息？既然都做完了，PM 还被激活干什么？

答案是：PM 在这段期间会多次被激活，但每次进入的是不同上下文。

图 2 · PM 的三种独立上下文

紫：每个子任务的独立审稿上下文；蓝：即时协作收件箱；黄：所有子任务通过后，原父 Work Item 才恢复并做整合。

5.1 子任务完成：生成独立 Review Work Item

以 copywriting 为例。执行者完成后，原子卡进入 AWAITING_MANAGER_REVIEW。系统先形成结构化 handoff，再创建一张独立的 review Work Item 给审稿人——默认是直属 manager，也可以由角色策略指定其他 reviewer。

PM 在这张独立 review 卡中只审当前交付：

  • approve：子卡进入 APPROVED；
  • reject：子卡进入 READY_FOR_REWORK，携带修改意见重新执行。

它不是在 PM 那张 WAITING_FOR_CHILDREN 父卡中审稿。这样做的价值是：审稿有自己的身份、状态、上下文和重试路径，不会污染父任务的整合语义。

5.2 执行中遇到阻塞：进入 Inbox / Comms

如果前端发现按钮文案冲突，可以给 Copywriter 或 PM 发送 blocker 消息。消息进入目标 Role Session 的 inbox；目标 Role 被唤醒处理后，原任务才能从 WAITING_FOR_PEER 恢复。

这也不是 PM 父卡的上下文，而是通信触发的临时协作上下文。

5.3 所有子任务通过：父 Work Item 做 Aggregate

只有当所有 direct children 都 APPROVED，PM 原来的父 Work Item 才从 WAITING_FOR_CHILDREN 恢复，进入 aggregate turn。

PM 此时不是重复执行子任务，而是做跨角色整合：统一文案、设计和代码，发现不一致，整理交付说明，再把结果交给更上一级或进入最终 deliver。

一句话：等待孩子的父卡只负责最终整合；单项审稿由独立 review 卡承担；中途协调走 inbox。一个 Role 可以被多次唤醒，但每次持有的业务上下文不同。

6 · 五种动作如何把一次任务推到交付

README 把 Self-Run 概括为五种动作。它们在运行时对应不同的 turn 和 Phase 变化：

动作运行时含义典型结果
Execute具体执行工作项完成后进入 manager review
Delegatemanager 调用 delegate_work 拆给直属下级父卡等待 children
Review在独立 review Work Item 中给 verdictapprove 或 rework
Integrate所有 children 通过后 aggregate形成上层统一交付物
Rework执行者带审稿反馈重新 execute再次进入 review
PM intake / dispatch └── copywriting (execute) ├── report / handoff └── PM review ├── approve → APPROVED └── reject → READY_FOR_REWORK → execute again └── design (depends_on: copywriting) └── frontend (depends_on: design) all children APPROVED └── PM aggregate └── deliver → user

7 · 阻塞不会只变成一句“我做不了”

真实任务不可能在开工前看见所有障碍。OpenOPC 把阻塞分成两个层级。

7.1 团队内部可以解决

Comms 是 Role 之间的通信机制，支持私信、广播、会议和系统通知。执行者发出需要回复的 blocker 后，自己的 Work Item 会等待 peer；接收方因新消息被重新激活，回复到达后原任务继续。

7.2 超出团队权限

如果问题涉及人类才能决定的方向、风险或权限，系统进入 Escalation，让 Work Item 处于 AWAITING_HUMAN。高风险工具调用也会通过 Approval 机制升级给人类，而不是让 Agent 默默执行。

判断方式可以简化为：

  • 同事能回答、经理能协调 → 走 Comms；
  • 方向、权限、高风险操作只有用户能决定 → 走 Escalation / Approval。

8 · Agent 本身是怎么运行的

OpenOPC 没有把 LangChain、CrewAI 或 AutoGen 当作核心 Agent 内核。项目有自己的 Native Runtime，负责模型回合、工具调用、上下文装配和公司模式契约；LiteLLM 负责连接和路由底层模型。

Role 可以使用的工具由角色配置和执行模式决定，主要分为：

工具组代表工具
文件与搜索file_read、file_write、grep、glob
执行与代码shell_exec、python_exec、git_diff
浏览器与 Webbrowser_navigate、web_search、web_fetch
公司协作delegate_work、send_dm、ask_peer_and_wait、manager_board_read
子 Agentagent_spawn、agent_wait、agent_send

Company Mode 的 manager 能不能拆活、能联系谁，并不只是 prompt 建议，而是由组织拓扑和工具调用边界共同约束；危险动作还要经过统一审批层。

9 · Self-Grown：成长主要记在人身上，知识再回到组织

Self-Run 完成后，系统已经有了最重要的归因线索：每张任务都携带 Employee Assignment，说明这项工作由哪个 Employee、以哪个 Role、在什么 domain 下完成。

Self-Grown 因此分两层学习。

9.1 Employee 层：形成个人履历

任务结果会更新该 Employee 的成功、部分成功、失败统计，并按 Role、domain 和 pattern 细分。系统据此形成：

  • Experience Score：特定岗位和领域下的经验分；
  • Delta Profile：高频成功做法、检查清单、审稿人和工具偏好、风险提醒；
  • Delta Context：把动态画像渲染成下一次执行时可注入的上下文。

所以 Alice 下次再做落地页时，不只带着“你是 Designer”的通用身份，还会带着“首屏要有 CTA、出图前冻结文案、检查三端适配”等自己的历史经验。

9.2 组织层：重复经验晋升为 Playbook

Reflection（反思）并不是让 LLM 重新通读完整聊天、自由写一篇复盘。运行过程中，各 Work Item 会先产出结构化 handoff 原料；整次交付结束、相关任务进入终态后，系统才按 Employee 分组，把这些结构化字段和可选用户反馈组装成复盘记录。

当同一 Employee 在同一个 Role + domain pattern 下至少积累两次 Reflection，而且成功做法、检查项等内容重复出现，系统可以把它晋升为一份 Playbook / Skill，以 SKILL.md 存入 Skill Library。

两条路径不要混淆：项目 Reflection 是从结构化执行原料按规则组装；反馈触发的 Self-Evolution 则可以由 manager 等 Role 经 LLM 产出员工经验 patch。它们都会影响员工经验，但不是同一条流程。

9.3 新员工如何继承

新员工从 Talent Template 入职时没有个人历史。它不会直接复制 Alice 的私人履历，但共享 Playbook 位于 Skill Library 中，后来的员工也能在运行时看到。

个人经验让老员工越来越值钱；共享 Playbook 让组织不会因为换人而失忆。

10 · 三个机制如何闭环

回到“AI 记账助手落地页”：

Self-Built先选组织和人

PM 走默认角色执行，Designer 复用 Alice，前端和文案从 Talent Template 招聘。

Self-Run逐层拆出 Work Item

PM 调用 delegate_work；文案完成后独立 review；设计和前端按 DAG 依次释放；阻塞走 inbox；全部通过后 PM aggregate 并 deliver。

Self-Grown把结果归因和沉淀

Alice 的成功记到她本人；前端第一次因响应式被 reject，形成风险提醒；重复有效经验晋升为共享 Playbook。

Next Run经验返回下一次组队

招聘器更愿意复用表现稳定的 Alice；新 Designer 即使没有履历，也能继承组织的落地页 Playbook。

11 · 它和普通多 Agent 编排的真正区别

普通多 Agent 流程OpenOPC
Agent 身份常和 prompt 绑定Role、Talent Template、Employee 分层
任务通常由预写 workflow 固定组织先存在，任务树由各层 manager 动态长出
完成后直接汇总文本执行、handoff、独立 review、rework、aggregate 分离
阻塞依赖自由对话Comms、Phase、Escalation 共同控制暂停与恢复
经验通常留在会话里按 Employee 归因，再把重复经验晋升为共享 Skill

这种设计当然更重：它引入组织配置、状态机、消息系统、审稿卡和经验存储。对于一个一次性小问题，Task Mode 更直接；对于跨角色、有审稿、有依赖、需要长期复用经验的复杂目标，Company Mode 才显示出价值。

12 · 上手：先跑一个最小公司任务

OpenOPC 要求 Python 3.10+，项目推荐用 uv。最小启动路径：

cd /path/to/OpenOPC
uv python install 3.12
uv venv --python 3.12
source .venv/bin/activate
uv pip install -e .

# 初始化配置、记忆、技能和项目目录
uv run opc init

# 在 .opc/config/llm_config.yaml 配置模型与 API key
# 启动 Office UI
uv run opc ui

打开 http://localhost:8765，创建会话并选择 Company Mode。也可以直接从 CLI 运行：

uv run opc chat -p demo \
  --mode company \
  --company-profile corporate \
  "为 AI 记账助手制作一套可交付的营销落地页"
第一次体验建议：不要只看最终回复。重点打开 Kanban、Agents、Comms 和 Execution Progress，观察 Work Item 怎样被拆出来、如何等待依赖、review 为什么是一张独立卡，以及 manager 何时从 WAITING_FOR_CHILDREN 回来 aggregate。

13 · 收束

如果只记住六句话：

  1. OpenOPC 的核心不是多启动几个 Agent，而是给 Agent 加上组织运行时。
  2. Role 是岗位，Talent Template 是候选人蓝图，Employee 是会积累经验的具体人。
  3. Self-Built 先选择组织架构，再为每个 Role 比较老员工与新人才。
  4. Self-Run 的任务树由各层 manager 用 delegate_work 逐层长出，Dependency DAG 决定并行与等待。
  5. PM 的父卡、单项 review 卡、inbox 是三个不同上下文；所有子任务通过后，父卡才回来 aggregate。
  6. Self-Grown 先把结果归因到 Employee，再把重复经验升级成整个组织可继承的 Playbook。
OpenOPC 想构建的，不是一次对话里看起来很忙的 Agent 群，而是一家公司在多次任务之后仍然知道：该招谁、该怎么协作、过去学到了什么。
