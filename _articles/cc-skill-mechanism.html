Anthropic · Claude Code

很多人把 Claude Code 的 skill 理解成"一段塞进系统提示词的指令模板"。实际上它是一套完整的三层架构：磁盘发现、轻量索引、专用工具按需展开。本文从源码出发，拆解 skill 从定义到执行的每一步。

一、先说问题：全量塞 prompt 的代价

假设你有 10 个 skill，每个 SKILL.md 平均 800 token。如果全量塞进系统提示词，每轮对话白烧 8000 token——不管用户用不用得到。skill 越多，context 越臃肿，有效对话空间越小。

Claude Code 的解法很直接：系统提示词里只放索引，完整内容用专用工具按需拉取。这就是所谓的渐进式披露（Progressive Disclosure）。

图 1：渐进式披露的三层架构

图 1：Claude Code 的 skill 渐进式披露架构。Tier 1 的索引常驻系统提示词，占用极小；Tier 2 和 Tier 3 只在模型决定调用时才产生 token 开销。

核心收益：系统提示词的 skill 开销从 O(N × skill_size) 降到 O(N × description_size)。skill 数量增长不会撑爆 context。

二、Skill 长什么样：SKILL.md 文件格式

每个 skill 是一个目录，核心文件叫 SKILL.md，带 YAML frontmatter。目录下还可以放附属文件：

.claude/skills/ ├── review-pr/ │ ├── SKILL.md ← 核心：frontmatter + 指令正文 │ └── references/ │ └── checklist.md ← Tier 3：按需加载 ├── commit/ │ └── SKILL.md └── debug/ ├── SKILL.md └── templates/ └── report.html

SKILL.md 的 frontmatter 有十几个可选字段，但核心只有两个必填：name 和 description。其余都是精细控制。

字段类型作用
namestring (必填)skill 标识符，如 review-pr
descriptionstring (必填)一句话描述，出现在系统提示词索引里
when_to_usestring告诉模型何时应该自动调用这个 skill
allowed-toolsstring[]skill 执行期间的工具权限白名单
modelstring执行时覆盖模型（haiku / sonnet / opus）
effortstring覆盖 thinking effort（low / high / max）
contextinline | forkinline 注入当前对话；fork 派子 agent 隔离执行
agentstringfork 模式下的 agent 类型（如 Bash）
pathsstring[]条件激活 glob——只在触碰匹配文件时 skill 才出现
user-invocablebool用户能否输入 /skill-name
disable-model-invocationbool禁止模型通过 Skill tool 调用
argumentsstring[]命名参数定义，正文用 $arg_name 引用
hooksobjectskill 运行时注册的 PreToolUse / PostToolUse hook

正文就是普通的 Markdown 指令。可以用 $ARGUMENTS 引用用户传入的参数，用 ${CLAUDE_SKILL_DIR} 引用 skill 目录路径。

关键设计：frontmatter 里的字段不只是"文档"，它们是运行时协议的一部分。allowed-tools 会注入权限白名单，model 会切换模型，context: fork 会改变执行模式。这些字段由 SkillTool 在执行时解析并生效。

三、四个来源：skill 从哪来

Claude Code 的 skill 有四个来源，启动时并行加载，同名高优先级覆盖低优先级：

来源路径加载方式
文件 skill .claude/skills/（项目级）
~/.claude/skills/（用户级）		 启动时扫描目录，懒加载内容
内置 skill src/skills/bundled/（编译进 CLI） initBundledSkills() 注册，如 verify、remember、loop、batch、debug
MCP skill MCP server 暴露 skill:// URI 调 resources/list 发现，前缀 mcp__<server>__
Plugin skill 插件系统注入 插件加载时注册
注意优先级：managed policy（企业策略）> user（用户级）> project（项目级）> additional dirs。同名 skill 高优先级覆盖低优先级。这意味着企业可以强制覆盖团队的 skill 定义。

除了启动时的静态扫描，Claude Code 还支持动态发现：会话进行中如果文件操作触碰了新的 .claude/skills/ 目录，discoverSkillDirsForPaths() 会自动扫描并注册新 skill，无需重启。

四、专用 Skill 工具：不只是 Read

这是 Claude Code skill 系统和"把指令塞 prompt 然后用 Read 工具读"的最大区别。Claude Code 注册了一个专门的 Skill 工具，模型可以用它来调用 skill。

Skill 工具的完整描述

这段文本出现在 Skill 工具自身的 tool definition 里，模型在每次对话都能看到：

Skill tool · getPrompt() 原文 
Execute a skill within the main conversation

When users ask you to perform tasks, check if any of the available skills match. Skills provide specialized capabilities and domain knowledge.

When users reference a "slash command" or "/<something>" (e.g., "/commit", "/review-pr"), they are referring to a skill. Use this tool to invoke it.

How to invoke:
- Use this tool with the skill name and optional arguments
- Examples:
  - `skill: "pdf"` - invoke the pdf skill
  - `skill: "commit", args: "-m 'Fix bug'"` - invoke with arguments
  - `skill: "review-pr", args: "123"` - invoke with arguments
  - `skill: "ms-office-suite:pdf"` - invoke using fully qualified name

Important:
- Available skills are listed in system-reminder messages in the conversation
- When a skill matches the user's request, this is a BLOCKING REQUIREMENT: invoke the relevant Skill tool BEFORE generating any other response about the task
- NEVER mention a skill without actually calling this tool
- Do not invoke a skill that is already running
- Do not use this tool for built-in CLI commands (like /help, /clear, etc.)
- If you see a <command-name> tag in the current conversation turn, the skill has ALREADY been loaded - follow the instructions directly instead of calling this tool again
在主对话中执行一个 skill

当用户要求你执行任务时，检查是否有可用的 skill 匹配。Skill 提供专门的能力和领域知识。

当用户引用"斜杠命令"或"/<something>"（如 "/commit"、"/review-pr"）时，他们指的是一个 skill。使用此工具来调用它。

如何调用：
- 使用此工具时传入 skill 名字和可选参数
- 示例：
  - `skill: "pdf"` - 调用 pdf skill
  - `skill: "commit", args: "-m 'Fix bug'"` - 带参数调用
  - `skill: "review-pr", args: "123"` - 带参数调用
  - `skill: "ms-office-suite:pdf"` - 使用全限定名调用

重要事项：
- 可用的 skill 列表在对话的 system-reminder 消息中
- 当 skill 匹配用户请求时，这是强制要求：在生成任何其他响应之前调用相应的 Skill 工具
- 绝不要提到一个 skill 却不实际调用此工具
- 不要调用已经在运行的 skill
- 不要对内置 CLI 命令使用此工具（如 /help、/clear 等）
- 如果你在当前对话轮次中看到 <command-name> 标签，说明 skill 已经被加载——直接遵循指令，不要再调用此工具

参数 schema

就两个字段，源码里的 Zod 定义：

z.object({
  skill: z.string().describe('The skill name. E.g., "commit", "review-pr", or "pdf"'),
  args:  z.string().optional().describe('Optional arguments for the skill'),
})

模型实际调用时长这样：

Skill(skill: "review-pr", args: "--focus security")

模型最终看到的对话内容：

<system-reminder>
The following skills are available for use with the Skill tool:

- commit: Create a commit with a descriptive message - Use when the user wants to commit changes
- review-pr: Review a pull request - Use when the user asks to review a PR
- pdf: Process and analyze PDF files
- verify: Verify changes work correctly - Use after making code changes
- my-plugin:do-thing: Does a specific thing (plugin)
</system-reminder>

每个 skill 一行，格式是 - name: description。如果有 when_to_use 字段，会拼在 description 后面，用 - 分隔。

索引的生成有几条约束：

  • 预算上限：整个索引块的 token 开销限制在 context window 的 1%。超限时，非内置 skill 的 description 会被截断，极端情况下退化为只有名字 - skill-name
  • 内置 skill 保护：bundled skill（如 verify、remember）的 description 永不截断
  • 过滤条件：只列出 type: 'prompt' 且 disable-model-invocation 不为 true 的 skill
  • 单条上限：每条 description 最多 1536 字符

这条 <system-reminder> 消息会随对话推进持续更新——新 skill 被发现或条件激活的 skill 生效时，索引会刷新。

六、Inline vs Fork：两种执行模式

Skill 有两种执行模式，由 frontmatter 的 context 字段控制：

① Inline 模式（默认）

skill 内容展开到当前对话，模型在同一个上下文里继续执行。相当于"把指令注入对话，模型接着干"。

context: inline共享 token budgetcontextModifier 生效

② Fork 模式

skill 内容喂给一个隔离的子 agent，子 agent 有独立的 token budget，跑完后只返回结果文本。相当于"派个子 agent 去干，拿结果回来"。

context: fork独立 token budget不带父对话历史

Fork 模式的真相

Fork 模式听起来很高级，但拆开看其实就是普通的 sub-agent：

// 伪代码，实际逻辑同构
runAgent(
  systemPrompt = general-purpose agent 的默认 prompt,
  userMessage  = SKILL.md 全文 + args,
  tools        = 父进程的完整工具集,
)

子 agent 收到的只有 skill 内容作为 user message，不带父对话的任何历史。系统提示词是 general-purpose agent 的默认 prompt，里面唯一关于"返回结果"的引导是一句话：

"When you complete the task, respond with a concise report covering what was done and any key findings — the caller will relay this to the user, so it only needs the essentials."

结果提取也很直接：extractResultText 取子 agent 最后一条 assistant message 的纯文本 blocks，tool_use / thinking / tool_result 全丢。没内容就返回默认的 "Skill execution completed"。

七、contextModifier：隐藏的运行时机制

inline 模式下，Skill tool 返回的不只是 newMessages，还有一个 contextModifier 函数。这个函数在当前 turn 的后续操作中生效，做三件事：

权限注入合并 allowedTools 到权限白名单

如果 skill 声明了 allowed-tools: [Bash(gh:*), Read]，这些工具在当前 turn 内免确认。模型可以直接调用，不用再弹权限框。

模型覆盖切换 mainLoopModel

如果 skill 声明了 model: sonnet，当前 turn 的后续模型调用切换到 Sonnet。会保留父会话的 [1m] suffix 避免丢失 context window。

Effort 覆盖切换 thinking effort

如果 skill 声明了 effort: high，当前 turn 的 thinking effort 切换。

为什么需要 contextModifier？因为 skill 不只是"一段指令"——它可能需要特定的工具权限（比如 commit skill 需要 Bash(git:*)）、特定的模型（比如轻量 task 用 haiku 省钱）、特定的 effort（比如 debug 需要 high effort）。contextModifier 让这些运行时配置和 skill 内容绑定，而不是靠用户手动设置。

八、条件激活：paths 字段

有些 skill 只在特定文件被触碰时才有意义。比如一个 api-review skill 只需要在修改 src/api/** 时出现。

paths frontmatter 就是为此设计的：

---
name: api-review
paths:
  - "src/api/**"
---

带 paths 的 skill 不会默认出现在 skill 列表里。只有当会话中文件操作触碰了匹配的 glob 模式，activateConditionalSkillsForPaths() 才把它们动态加入可用列表。

具体怎么进入上下文

触发链路是：模型调用 FileEdit / FileWrite / FileRead → 工具内部调 activateConditionalSkillsForPaths([filePath], cwd) → 匹配成功则把 skill 从 conditionalSkills 移到 dynamicSkills → 触发 skillsLoaded.emit() 缓存失效 → 下一轮重新生成 skill 索引时，新激活的 skill 出现在列表里。

举个例子。假设你有一个条件 skill：

---
name: api-review
description: Review API endpoint changes for security and correctness
paths:
  - "src/api/**"
---

会话开始时，skill 索引里没有 api-review。当模型编辑了 src/api/users.ts：

触发模型调用 FileEdit 编辑 src/api/users.ts

FileEdit 工具执行成功后，内部调用 activateConditionalSkillsForPaths(["src/api/users.ts"], cwd)。glob src/api/** 匹配，api-review 被移入可用 skill 列表。

下一轮增量追加一条 skill listing 消息

下一轮生成 attachment 时，系统发现 api-review 还没宣布过 → 追加一条新的 <system-reminder> 消息。旧的 skill listing 不删不替换，两条同时发给 API。

模型实际看到的 messages 数组：

[...之前的对话...]

<system-reminder>                          ← 第一条，会话开局时生成
The following skills are available for use with the Skill tool:

- commit: Create a commit with a descriptive message
- review-pr: Review a pull request
- pdf: Process and analyze PDF files
</system-reminder>

[...中间的对话：用户发消息 → 模型编辑了 src/api/users.ts ...]

<system-reminder>                          ← 第二条，条件激活后增量追加
The following skills are available for use with the Skill tool:

- api-review: Review API endpoint changes for security and correctness
</system-reminder>

user: 继续...

两条 <system-reminder> 各自只包含当时新宣布的 skill，不会重复。模型能从第二条里发现 api-review 并通过 Skill tool 调用。因为是 append 而非 replace，已有的 prompt cache 前缀不受影响。

一个潜在的歧义：两条消息用的是完全相同的 header——"The following skills are available for use with the Skill tool:"，没有"新增"/"增量"之类的标记。模型可能把第二条理解为"当前可用 skill 的完整列表"，从而降低调用第一条里 commit、review-pr 等 skill 的概率。isInitial flag 在渲染时没有被用来区分措辞。
这解决了一个实际问题：如果你有 50 个 skill 但每次只用到 5 个，条件激活让系统提示词里的索引保持精简，只展示当前上下文相关的 skill。

九、双入口：用户手动 vs 模型自动

Skill 有两个调用入口：

入口 A：用户输入 /skill-name

用户在 CLI 里输入 /review-pr --focus security，processSlashCommand 拦截并展开 skill 内容到对话。模型看到的不是 /review-pr 这个字符串，而是展开后的指令。

展开后注入对话的消息结构：

processSlashCommand.tsx · 展开后的消息结构 
// messages[0]: metadata breadcrumb (visible to model as user message)
{
  role: "user",
  content: "<command-name>/review-pr</command-name>\n<command-message>review-pr</command-message>\n<command-args>--focus security</command-args>"
}

// messages[1]: full SKILL.md content (isMeta=true, hidden from UI)
{
  role: "user",
  isMeta: true,
  content: "# Review PR\n\nReview the current pull request...\n\nFocus: $ARGUMENTS\n\n## Steps\n1. Read the diff\n2. Check for security issues\n3. ..."
  // $ARGUMENTS replaced with "--focus security"
}

// messages[2]: attachment (command_permissions)
{
  type: "attachment",
  attachmentType: "command_permissions",
  allowedTools: ["Bash(gh:*)", "Read"],  // from frontmatter
  model: "sonnet"                          // from frontmatter
}
// messages[0]: 元数据面包屑（模型可见的 user message）
{
  role: "user",
  content: "<command-name>/review-pr</command-name>\n<command-message>review-pr</command-message>\n<command-args>--focus security</command-args>"
}

// messages[1]: SKILL.md 全文（isMeta=true，UI 不显示）
{
  role: "user",
  isMeta: true,
  content: "# Review PR\n\nReview the current pull request...\n\nFocus: $ARGUMENTS\n\n## Steps\n1. Read the diff\n2. Check for security issues\n3. ..."
  // $ARGUMENTS 被替换为 "--focus security"
}

// messages[2]: 附件（command_permissions）
{
  type: "attachment",
  attachmentType: "command_permissions",
  allowedTools: ["Bash(gh:*)", "Read"],  // 来自 frontmatter

}

注意 messages[1] 的 isMeta: true——UI 不显示这条消息，但模型能看到。同时 addInvokedSkill() 注册了这次调用，确保对话压缩时 skill 内容不会丢失。

入口 B：模型调用 Skill 工具

模型根据系统提示词里的 skill 索引 + when_to_use 描述，判断需要时主动调 Skill(skill: "review-pr", args: "--focus security")。执行路径和入口 A 最终走到同一个 getMessagesForPromptSlashCommand 函数，注入的消息结构完全一样。

一个微妙的重叠：系统提示词告诉模型"用户引用 /something 时，用 Skill tool 调用"。但实际上用户输入 /skill-name 会被 harness 层先拦截展开，模型根本看不到 /something。这句指引的真正作用是让模型在非 CLI 客户端（web、API）或用户自然语言提到 skill 名字时，能主动调用。

十、从 CC 的设计里能学到什么

Claude Code 的 skill 系统本质上解决了三个问题：

① Token 效率

渐进式披露让 skill 数量和 context 开销脱钩。你可以有 100 个 skill 而不用担心系统提示词爆炸。

Tier 1 索引 ≤ 1%按需加载全文

② 运行时控制

skill 不只是"一段文字"，它能携带权限、模型、effort、hook 等运行时配置，通过 contextModifier 在执行时生效。

allowed-toolsmodel overrideeffort override

③ 执行隔离

fork 模式让 skill 在隔离的子 agent 里执行，不污染主对话上下文。适合"做完就走"的独立任务。

独立 token budget不带历史结果自包含

如果你在设计自己的 agent 系统，最小可行方案是：

  1. 定义层：SKILL.md + YAML frontmatter 存元数据
  2. 工具层：注册一个 Skill tool（或拆成 list_skills + invoke_skill），系统提示词只注入索引
  3. 调用层：模型调 tool → 读 SKILL.md → 注入对话或派子 agent

不需要一开始就做齐所有特性。渐进式披露 + 专用工具这两步就能解决 80% 的问题。
