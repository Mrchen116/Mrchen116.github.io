Claude Code vs Codex：Coding Agent 如何做长程任务

一个 coding agent 的核心是 agent loop：LLM 和工具之间的循环交互。当 LLM 决定不再调用工具时，loop 退出，agent 停下来。但任务可能远未完成。本文拆解 Claude Code 和 OpenAI Codex 如何让 agent 在 loop 退出后还能被自动唤醒、继续工作，以及两种截然不同的设计哲学。

1 · 核心问题：agent loop 退出之后怎么办

一个 coding agent 的核心是一个 agent loop——LLM 和工具之间的循环交互。假设用户说"帮我重构整个认证模块"，agent 的执行过程是这样的：

图 1：agent loop 的工作方式

图 1：agent loop。LLM 和工具之间反复交互，中间可能有几十轮。当某一轮 LLM 只返回文本、不调工具时，loop 退出。

关键机制：只要 LLM 的回复中包含工具调用，loop 就继续；一旦 LLM 只返回文本，loop 就退出。一个 turn（用户的一条消息）内部可能有几十轮 LLM ↔ 工具交互，耗时可能超过 10 分钟。

问题来了：当 LLM 决定"我这轮不调工具了"，agent loop 就退出了。但任务可能还没做完——也许还有 20 个文件没改，也许测试还没跑，也许需要等 CI 结果再继续。loop 退出后，agent 就彻底停了，等用户下一条消息才能动。

用户不可能每 30 秒手动发一条消息来推 agent 继续干活。agent 需要一种能力：在 agent loop 退出之后，还能被自动唤醒，继续执行。

Claude Code 和 Codex 都解决了这个问题，但走了两条不同的路。

2 · Claude Code：agent 自己设闹钟

Claude Code 的核心思路是：agent 是一个持久的 REPL 进程，有 5 种不同的事件源可以唤醒它。在 agent loop 执行过程中，agent 可以主动注册这些事件源（比如"把命令放后台跑"）。当 LLM 不再调用工具、loop 退出后，agent 进入 idle。事件到达时，agent 被唤醒，启动新的 turn，继续工作。

2.1 五种事件源

Claude Code 给 agent 提供了 5 个工具，每个都是一个独立的事件源。agent 在执行过程中可以按需注册，然后进入 idle 等待通知。

① Bash run_in_background —— 等命令跑完

把一个 shell 命令放到后台执行。命令结束时，agent 收到一条 task-notification，包含 stdout/stderr。

场景：跑测试、构建、部署触发：命令退出次数：一次

② Agent run_in_background —— 等子 agent 完成

派一个子 agent 去执行复杂任务（比如"搜索所有文件找出认证相关代码"）。子 agent 完成后，主 agent 收到通知和结论。

场景：并行搜索、代码审查触发：子 agent 结束次数：一次

③ Monitor —— 持续监听事件流

后台运行一个命令，每次 stdout 输出一行就通知 agent 一次。适合需要持续关注的场景。

场景：监控日志、文件变更、WebSocket触发：每行输出次数：无限

④ CronCreate —— 定时触发

用标准 cron 表达式注册一个定时任务。到了时间点，agent 被唤醒执行指定的 prompt。

场景：定时检查、定期汇报触发：cron 匹配次数：循环或一次性

⑤ ScheduleWakeup —— 自主迭代节奏

agent 自己决定"过 N 秒再来看一眼"。用于 /loop 模式下的自主迭代——agent 每轮结束后安排下一次唤醒，直到任务完成。

场景：轮询外部状态、迭代搜索触发：延迟到期次数：每次手动注册

2.2 实际例子：agent 怎么用这些工具

假设用户说"帮我跑测试，全部通过后部署到 staging"。第一个 turn 内部，agent loop 跑了很多轮：

LLM 第 1 轮读代码、了解项目结构

LLM 返回 3 个工具调用：Read 读 pyproject.toml、Read 读测试配置、Glob 找测试文件。执行，结果回传。

LLM 第 2 轮决定跑测试

LLM 返回 1 个工具调用：Bash({ command: "pytest -x", run_in_background: true })。测试在后台跑，agent 注册了事件源。

LLM 第 3 轮没有更多工具要调了

LLM 返回纯文本："测试已在后台运行，完成后我会继续部署。"——没有工具调用 → agent loop 退出 → agent 进入 idle。

task-notification5 分钟后，测试完成

task-notification 到达。agent 被唤醒，启动新的 turn。

LLM 第 1 轮检查测试结果

LLM 返回工具调用：读测试输出文件。全部通过。

LLM 第 2 轮开始部署

LLM 返回工具调用：Bash({ command: "deploy staging", run_in_background: true })。部署在后台跑。

LLM 第 3 轮纯文本，loop 退出

"部署已在后台运行。" → 无工具调用 → agent loop 退出 → idle。

task-notification部署完成

agent 唤醒，新 turn 内汇报结果。

整个过程用户只说了一句话，跨了 3 个 turn（每个 turn 内部有多轮 LLM ↔ 工具循环），agent 自主完成了"读代码 → 跑测试 → 等结果 → 部署 → 等完成 → 汇报"的完整链路。关键转折点：每次 agent loop 退出时，都有一个后台事件源在等着唤醒它。

2.3 Monitor 的例子：持续监控

更复杂的场景——用户说"盯着 CI，有问题告诉我"：

主 agent注册 Monitor

Monitor({ command: "gh pr checks 123 --watch", timeout_ms: 600000 })

Monitor持续推送事件

每次 CI 状态变化，stdout 输出一行，agent 收到一条通知。可能 10 分钟内收到 15 条通知。

主 agent发现失败

收到一条 "lint: failure" 通知，agent 立刻分析原因，向用户汇报。

2.4 核心机制：task-notification 是统一的唤醒信号

不管事件源是什么——命令结束、子 agent 完成、Monitor 输出一行、Cron 触发、Wakeup 到期——最终到达 agent 的都是同一种东西：task-notification。

关键设计：统一的唤醒协议意味着 agent 不需要关心"谁叫醒了我"。它只需要拿到通知里的数据（命令输出、子 agent 结论、Monitor 事件），决定下一步做什么。这和人的工作方式很像——手机响了，你看一眼通知，决定要不要处理。

3 · Codex：框架帮你续跑

Codex 的思路完全不同：不给 agent 主动注册事件源的能力，而是通过生命周期钩子让框架自动续跑。

图例： 生命周期钩子 GoalExtension 注入 prompt 续跑

3.1 Goal 机制

Codex 有一个独特的概念：Goal。用户可以给 agent 设定一个目标（比如"重构认证模块"），框架会确保 agent 在 idle 时自动续跑，直到 goal 完成。

具体流程：

用户设定 Goal

"重构认证模块，所有测试通过后标 complete。"

框架记录 goal，status = Active

goal 信息写入 state_db：{ objective: "重构认证模块", status: Active, token_budget: 50000 }

Agent第一轮工作

读文件、改代码、跑测试。turn 结束。

框架触发 on_thread_idle

turn 结束 → 没有活跃 turn → 没有待处理 mailbox → 调用所有扩展的 on_thread_idle。

GoalExtension检查 goal 状态

从 state_db 查 goal：status == Active → 还没完 → 注入 continuation prompt → 启动新 turn。

Agent第二轮工作

继续改代码。这轮做完后，调用 update_goal("complete")。

框架goal 完成

下一次 on_thread_idle → GoalExtension 查到 status == Complete → 不续跑 → agent 停下来。

3.2 continuation prompt 长什么样

GoalExtension 注入的不是简单的一句"继续干"，而是一个完整的行为约束模板：

Continue working toward the active thread goal.

<objective>
{{ objective }}
</objective>

Continuation behavior:
- This goal persists across turns. Ending this turn does not require
  shrinking the objective to what fits now.
- Keep the full objective intact. If it cannot be finished now, make
  concrete progress toward the real requested end state.

Budget:
- Tokens used: {{ tokens_used }}
- Token budget: {{ token_budget }}
- Tokens remaining: {{ remaining_tokens }}

Completion audit:
Before deciding that the goal is achieved, treat completion as unproven
and verify it against the actual current state:
- Derive concrete requirements from the objective.
- For every requirement, inspect authoritative evidence.
- Treat uncertain or indirect evidence as not achieved.
- Only mark the goal achieved when current evidence proves every
  requirement has been satisfied.

Blocked audit:
- Do not call update_goal("blocked") the first time a blocker appears.
- Only use status "blocked" when the same blocking condition has
  repeated for at least three consecutive goal turns.
设计亮点：这个 prompt 包含了三个关键约束——不要缩小目标、完成前必须逐条审计、不能轻易放弃。这让 agent 在无人监督下也能按正确方式自主推进。

3.3 另一个唤醒源：Mailbox

除了 Goal 自动续跑，Codex 还有 agent 间通信的唤醒机制：

子 Agent发送消息

通过 InterAgentCommunication 发消息，trigger_turn: true。

框架检查 session 状态

消息入 mailbox → 调 maybe_start_turn_for_pending_work → session 空闲 → 立即启动新 turn。

这和 Claude Code 的 SendMessage + task-notification 效果一样——agent 之间可以直接互相唤醒。

4 · 对比：两种哲学

Claude Code —— agent 驱动

agent 自己决定"要不要设闹钟、盯什么日志、轮询什么状态"。不设就停。工具齐全但需要 agent 主动使用。

Codex —— 框架驱动

goal 设定后框架自动续跑，agent 要主动喊停。生命周期钩子让扩展可以在 idle 时自动注入工作。

能力 Claude Code Codex
用户发消息唤醒 ✅ ✅
其他 agent 发消息唤醒 ✅ SendMessage + task-notification ✅ Mailbox + trigger_turn
后台命令/任务完成 ✅ Bash run_in_background ❌
持续事件流监控 ✅ Monitor（文件/WebSocket/命令） ❌
定时触发 ✅ CronCreate ❌
延迟唤醒 ✅ ScheduleWakeup ❌
目标驱动自动续跑 ❌（靠 agent 自己 ScheduleWakeup） ✅ GoalExtension + on_thread_idle
生命周期钩子扩展 ❌（工具硬编码） ✅ ThreadLifecycleContributor
桌面/手机通知 ✅ PushNotification ✅ 终端通知（OSC9/BEL）

4.2 一句话总结

Claude Code 是"手动挡但工具齐全"——agent 自己决定要不要设闹钟、盯什么日志、轮询什么状态。Codex 是"自动驾驶"——goal 设定后框架默认续跑，agent 要主动喊停才能停。

5 · 各自的取舍

5.1 Claude Code 的代价

agent 驱动意味着模型必须足够聪明，知道什么时候该用什么工具。如果模型不知道该调 Monitor 而是傻等，或者设了一个太长的 ScheduleWakeup，任务就会卡住。工具的正确使用完全依赖模型的判断力。

另外，5 个事件源是硬编码的。想要新的事件源（比如"文件变更触发"），必须在 harness 层面新增工具，agent 自己无法扩展。

5.2 Codex 的代价

框架驱动意味着灵活性受限。没有 Monitor——agent 不能自己盯日志。没有 Cron——agent 不能定时检查状态。没有 ScheduleWakeup——agent 不能自己决定"过会儿再来看"。

agent 只能被用户、其他 agent、或 goal 续跑唤醒。如果一个任务需要"每隔 5 分钟检查一次外部 API"，Codex 的 agent 做不到——它没有工具来表达这个意图。

但 Codex 有 CC 没有的东西：on_thread_idle 生命周期钩子是一个可扩展的框架——任意扩展都可以注册这个钩子，在 agent 空闲时自动注入工作。CC 的 5 个事件源是固定的，Codex 的扩展能力理论上更强，只是目前只有 GoalExtension 这一个实现。
