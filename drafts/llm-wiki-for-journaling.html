LLM Wiki · Knowledge Architecture

LLM Wiki 是什么

LLM Wiki 不是“让模型帮我总结文档”，也不是传统 RAG 的换皮。我现在的理解是：它让 LLM 持续维护一套结构化、互相链接、可被再次查询和更新的 Markdown wiki，把零散资料编译成会积累的知识层。

这篇笔记的主线：先讲 Karpathy 的思想，再讲目录结构，再讲关键动作流程，最后才落到个人日记体系。日记只是这个方法论的一个应用场景，不是 LLM Wiki 的全部。

1 · Karpathy 的思想

Karpathy 提出 LLM Wiki，是在反思大多数人使用 LLM 和文档的方式：把一堆资料丢给系统，然后在提问时让模型检索相关片段并生成答案。这就是常见的 RAG 体验。

RAG 有用，但它有一个隐含问题：每次回答都像重新开卷考试。模型每次都要重新找片段、重新拼上下文、重新综合判断。资料之间的关系没有被稳定沉淀下来，前一次问题里的洞察也不会自然进入下一次问题。

LLM Wiki 的转向是：不要只在 query time 检索 raw documents，而是在资料进入系统时，就让 LLM 把资料吸收到一个持久 wiki 里。也就是说，知识不是每次问答时临时拼出来，而是平时就被编译和维护。

问题 RAG 的做法 LLM Wiki 的做法
新资料来了 切 chunk，建索引，等以后检索。 阅读资料，抽取信息，更新 source/entity/concept/synthesis 页面。
回答问题 从 raw chunks 临时找证据。 先读 wiki 的 index 和相关页面，再必要时回到 raw source。
跨文档洞察 每次临时综合。 沉淀成 synthesis 页面，后续继续复用和修正。
维护成本 人很快懒得整理。 LLM 负责摘要、归档、交叉链接、更新索引和日志。

我理解 Karpathy 的核心判断是：知识库真正难的不是存储，而是维护。 人可以读资料、提问题、做判断，但很难长期坚持更新链接、修正旧结论、整理索引、拆分页面。LLM Wiki 把这部分“簿记劳动”交给 agent。

所以我会把 LLM Wiki 理解成三层：

层 含义 谁负责
raw sources 原始资料。文章、论文、日记、会议记录、网页、图片、代码仓库等。它是 source of truth。 人负责收集，LLM 只读不改。
wiki LLM 生成和维护的 Markdown 知识库。里面有来源页、实体页、概念页、比较页、综合页、索引和日志。 LLM 负责写、改、链接、拆分、合并。
schema 规则文件，例如 AGENTS.md 或 CLAUDE.md。定义目录、页面格式、ingest/query/lint 流程。 人和 LLM 共同演化。

这个架构对我最有启发的地方在于：raw source 是证据，wiki 是理解，schema 是维护规则。LLM Wiki 不是把原文搬运成摘要，而是把原始材料编译成更适合长期思考的知识层。

2 · 目录结构

Karpathy 原文没有规定唯一目录结构，它强调的是模式：raw sources 只读，wiki 由 LLM 维护，schema 约束 agent 行为。如果我要把这个模式落成文件系统，一个通用版本大概会长这样：

llm-wiki/ ├── AGENTS.md # schema：最重要的规则文件，约束 agent 如何维护 wiki ├── README.md # 给人看的项目说明：这个 wiki 的主题、边界、使用方式 ├── inbox.md # 待处理入口：URL、PDF、repo、笔记路径、处理深度 ├── raw/ # 原始资料层；source of truth；LLM 只读不改 │ ├── articles/ # 网页、博客、长文 │ ├── papers/ # 论文、报告 │ ├── books/ # 书籍摘录、章节笔记 │ ├── transcripts/ # 播客、访谈、会议、视频字幕 │ ├── notes/ # 人手写的原始笔记 │ ├── repos/ # 代码仓库、README、设计文档 │ └── assets/ # 图片、附件、PDF 截图等非纯文本材料 ├── wiki/ # LLM 维护的知识层；人主要读这里 │ ├── index.md # 内容导航：页面列表、摘要、别名、分类、来源数 │ ├── overview.md # 全局概览：当前 wiki 对主题的整体理解 │ ├── log.md # 时间日志：ingest/query/lint/cleanup 做了什么 │ ├── gaps.md # 缺口清单：缺资料、缺页面、待追问的问题 │ ├── contradictions.md # 冲突清单：新旧资料或页面之间的不一致 │ ├── sources/ # 来源页：一份 source 对应一张“证据卡片” │ ├── entities/ # 实体页：人、公司、项目、产品、地点、组织等 │ ├── concepts/ # 概念页：方法、思想、模式、主题、技术概念 │ ├── topics/ # 主题页：比 concept 更宽的领域或问题簇 │ ├── comparisons/ # 比较页：多个实体、方案、观点之间的对照 │ └── syntheses/ # 综合页：跨来源结论、重要 query 的沉淀答案 └── state/ # 机器状态；辅助 agent 维护，不是主要阅读层 ├── source_manifest.json # source 的路径、hash、ingest 状态 ├── backlinks.json # 反向链接索引，由脚本或 agent 重建 └── last_run.json # 上次运行信息，避免重复处理

这里有几种页面很容易混在一起，我会这样区分：

页面类型 根据什么写 价值
source page 一份来源文档。 把原始资料标准化成可读、可引用、可追溯的证据卡片。
entity page 多个来源里反复出现的具名对象。 聚合这个实体的事实、变化、关系和来源。
concept page 多个来源里反复出现的主题、模式或方法。 把分散的观察抽象成可复用的理解。
synthesis page 一次重要查询或跨来源分析。 把已经做过的思考保存下来，避免下次重新推理。

Farzaa 的 personal wiki 更强调目录从资料里自然生长。它给出的参考类型非常丰富：people/、projects/、places/、events/、books/、tools/、philosophies/、patterns/、tensions/、decisions/、transitions/、relationships/、skills/、ideas/ 等。但我觉得更重要的是它的克制：不要预先把目录建满，目录应该从数据里长出来。

一个关键判断：source-centric wiki 是好起点，但不是完整终点。真正有复利的是 source page、entity page、concept page、synthesis page 一起工作。source page 保证证据，entity/concept/synthesis 页面负责沉淀理解。

3 · 关键动作流程

LLM Wiki 不是一个静态目录，而是一组动作。目录只是结果，真正让它有用的是 agent 每次都按固定流程维护它。换句话说，我不能只设计文件夹，还要设计 agent 怎么工作。

Init初始化 wiki

确定主题和边界，创建 raw/、wiki/、AGENTS.md、index.md、log.md。最重要的是写清楚规则：raw 不改，wiki 可改；先读 index；更新页面前必须读原页面；所有判断要保留来源。

Ingest吸收新资料

把新资料放进 raw/ 或 inbox.md。agent 读取资料，生成 source page，抽取实体和概念，更新已有 entity/concept 页面，必要时创建新页面，最后更新 index、backlinks 和 log。Karpathy 的设想里，一份重要 source 可能会影响 10 到 15 个 wiki 页面。

Query回答问题

回答问题时不要先翻 raw。先读 index.md，再读 3 到 8 个相关页面，沿着 wikilink 和 related 字段扩展。答案要明确引用哪些 wiki 页面支持了判断，wiki 不知道的就说不知道。

Promote把好答案写回 wiki

如果一次 query 产生了长期有价值的比较、判断或框架，不要让它留在聊天记录里。把它整理成 syntheses/ 页面，再更新相关页面的链接。

Lint健康检查

周期性检查 broken links、孤立页面、重复页面、过胖页面、过时结论、缺少来源的判断、重要概念没有页面、不同页面之间的冲突。Lint 的目的不是新增内容，而是让知识库不腐烂。

Cleanup重构和拆分

当一个页面变成流水账，或者一个概念被塞进太多不相关页面，就要拆分、合并、重命名、修复反链。Farzaa 特别强调，文章要按主题组织，不要按日记时间线机械堆叠。

把这些动作串起来，我理解的 LLM Wiki 生命周期是这样的：

init
  建目录、写规则、创建 index/log

ingest source
  raw source -> source page -> entities/concepts -> syntheses -> index/log

query
  question -> index -> relevant pages -> answer

promote answer
  useful answer -> synthesis page -> backlinks/index/log

lint / cleanup
  check drift, gaps, contradictions, broken links, stale pages

这套流程里最重要的动作其实是“更新已有页面”。如果每份资料只生成一份孤立摘要，那只是一个摘要库。LLM Wiki 的核心是：新资料进入时，它会改变旧页面，修正旧理解，增强旧链接。

4 · 对个人日记体系的启示

回到我的个人日记体系，这套思想的启发不是“把日记写得更复杂”，而是把日记放到 LLM Wiki 的三层结构里看。

LLM Wiki 层 个人日记里的对应物
raw sources 每日原始日记、每周自我总结、聊天记录、项目记录。
wiki 人物、人生阶段、patterns、books、projects、decisions。
schema 我给 agent 写的日记流程规则，比如人物画像怎么写、什么时候更新索引、哪些判断只能放待观察点。

我现在的“人物画像流程”已经是一个小型 LLM Wiki。它做了四件事：识别人物，读取人物索引，更新已有画像，必要时新建页面。区别只是它目前只覆盖 people/ 这一类实体。

按 LLM Wiki 的思路，它可以自然扩展，但不需要一次扩很多。对我来说，更合理的方式不是照搬 Farzaa 的几十个类型，而是从我平时写日记时会反复思考的问题倒推目录。第一版我会先保留这几个：

类型 对应的问题
people/ 这个人是谁？我和他发生过什么？我对他的判断有没有变化？
periods/ 我现在处在哪个人生阶段？比如研究生阶段、创业阶段、转型阶段，它的主线是什么？
patterns/ 我是不是反复进入同一种行为循环？触发条件、反应、结果分别是什么？
books/ 哪些书真正影响了我的判断？它们改变了我对什么问题的看法？
projects/ 我长期投入的项目在怎么变化？动力、阻力、阶段性判断是什么？
decisions/ 我当时为什么做这个选择？有哪些备选方案？后来是否证明判断成立？
我会采用的节奏：每天只写 raw 日记。每周总结时做一次 wiki 更新。这样既符合 Karpathy 的“持续吸收”，又不会让日记系统变成每天维护知识库的负担。

所以，对我的日记体系来说，LLM Wiki 不是替代日记，而是在日记之上增加一层长期记忆。日记保存当天发生了什么，wiki 保存这些事情长期说明了什么。日记是时间流，wiki 是理解网。
