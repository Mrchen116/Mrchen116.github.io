Skill 自进化 · 参考工作对比

SkillOpt vs Trace2Skill：从轨迹到 skill 变更，两种做法画给你看

两个工作都在做同一件事——读一批执行轨迹，把"教训"沉淀成更好的 agent skill。但具体怎么走，分歧不小。本文用三张流程图把两者讲清楚，再并排标出区别。

1 · 它们共享的骨架

抛开细节，两者都是同一条主干：带着 skill 去干活 → 得到轨迹 → 分析轨迹找"该改什么" → 把改动合并 → 写回 skill → 验证好不好。区别藏在每一站具体怎么做，尤其是分析、合并、skill 的形态和验证这四站。先各看一张完整流程图，再并排对比。

一句话先记住：SkillOpt 把一份 单个 SKILL.md 当"参数"来训；Trace2Skill 进化的是一个 skill 目录（含 references 多文件），还会真去环境里复现失败来验证根因。

2 · SkillOpt 的流程

把 skill 当神经网络参数来"训"：跑一批带标准答案的题，按对错把轨迹分两桶，各自找共性、提出有限的几条改动，合并打分排序，写进 skill，最后在留出集上验收——只有分数严格变高才接受。

图 1 · SkillOpt：单文件 skill 的"训练循环"

图例：主流程步骤 失败侧 成功侧 / 产物 验证闸门。橙色虚线 = 被拒改动回流当负反馈。

3 · Trace2Skill 的流程

它不止改单文件，而是进化一个 skill 目录。最大不同在分析：失败轨迹交给一个会动手的 agent——它真去复现失败、打个最小补丁、重新对标准答案测一遍，修对了才确认根因。之后把各任务的"教训"并行提成补丁，再无冲突地合并进目录。

图 2 · Trace2Skill：skill 目录的 map-reduce 进化

图例：进化步骤 失败侧（★ agentic 验证驱动） 成功侧 / 产物 复查。注：进化阶段本身没有性能 gate（只格式校验+回滚），图中失败侧★就是它唯一依赖标准答案的环节。

5 · 同一个例子，两边各走一遍

抽象流程看完，用一个具体例子把每个环节走一遍，差别会更扎实。

例子设定

Skill：xlsx（表格操作）。当前 SKILL.md 的「## 区间公式」一节只写了"用 SUM/AVERAGE 对区间求值"，没说怎么确定区间。

最近一批 5 段用到该 skill 的轨迹（任务都是"对某一列求和"）：

  • 失败 ×3：写的 SUM 区间含了表头行（或漏掉最后一行）→ 结果错、被用户纠正。
  • 成功 ×2：先查了数据行数 / 区域再写 SUM → 一次做对。
环节SkillOpt 对这个例子做的Trace2Skill 对这个例子做的
① 轨迹来源 在数据集上现跑这批求和题（带标准答案）→ 5 段轨迹 ＋ 对错分：3 错(hard=0) / 2 对(hard=1)。 跑 benchmark ＋ 对标准答案评测 → 同样分出 3 失败题 / 2 成功题。
② 分析"改什么" 失败桶(3 段)喂 analyst_error → 读出共性"SUM 区间含表头/漏末行"；成功桶(2 段)喂 analyst_success → 共性"先查数据区域再写公式"。各产一条改动建议。
从轨迹文本里推断根因。		 失败题逐个交给会动手的 agent：它打开 input.xlsx 复现 → 把区间改成跳过表头 → 重测对标准答案，通过 → 确认根因＝"区间含表头行"；产 失败原因 ＋ 教训"写区间公式前先定数据区域边界"。成功题单遍蒸馏赢法"查行数→定区域→写 SUM→校验"。
动手复现验证根因。
③ 合并改动 失败改动 ＋ 成功改动合并(失败优先)；两条都指向"先定数据区域" → 支持数＝失败 3 ＋ 成功 2，很高 → 排序靠前，预算 L 内保留。 5 条记录各提一个补丁 → 无冲突合并：3 个失败补丁都说"定数据区域" → 去重成一条(反复出现＝高优先)；决定把细节拆成 references/data-region.md，于是"建该文件 ＋ 在 SKILL.md 加链接"成对保留。
④ 写进 skill 改单个 SKILL.md——「## 区间公式」节追加一句：
写区间公式前先确定数据区域(跳过表头、含最后一行)，并用一次小检查确认。		 改skill 目录——SKILL.md「## 区间公式」加一句要点 ＋ 链接；新建 references/data-region.md 写详细的"如何探测数据区域"步骤（要点留主文件、细节进 references）。
⑤ 验证 改完的 skill 在留出集重跑求和题：分数严格更高 → 接受；否则撤销，改动进拒绝缓冲。 没有"改完重跑打分"的环内验证。补丁写进目录后只做格式校验（行数/链接/frontmatter），不重跑 agent、不按性能 accept/reject。它对"这条改动好不好"的唯一 gold 依赖发生在更早的分析阶段（会动手的 agent 复现+重测 gold 确认根因）。
产物 一份更新后的 SKILL.md（多了一条"定区域"规则）。 一个更新后的 skill 目录：SKILL.md 多一句＋链接，且多了 references/data-region.md。
这个例子里最能看出的两处不同：② SkillOpt 靠"读轨迹推断"，Trace2Skill 靠"动手复现+重测确认"；④ SkillOpt 只动单文件，Trace2Skill 能把细节另起一个 references 文件并保证链接不断。⑤ 只有 SkillOpt 靠"带答案重跑"做环内 gate（每处改动重测、严格更高才收）；Trace2Skill 没有环内性能 gate，它的 gold 依赖在更早的"分析时根因验证"。两者的 gold 依赖在线都没有——而我们**也不重建效果反馈**：对齐最成熟的在线方案 Hermes（它刻意不衡量"改动有没有效"），质量靠入口只在反复≥2才改 ＋ 每改可逆（快照/archive）＋ 持续进化自然收敛 ＋ Curator 周期维护，不做"测效果/复发回滚"。

6 · 哪个更适合"在线"场景

关键事实：两者最讲究的"验证"在在线场景都用不了——SkillOpt 的留出集闸门、Trace2Skill 的 agentic 重测，都依赖"标准答案 ＋ 可重放环境"。线上是真实用户在用，既没有 gold，也不能把同一题反复跑。所以两者的"质量保险"我们都得换成别的——而且**不去重建一个在线版的效果反馈**（最成熟的在线方案 Hermes 本就不衡量改动有没有效）：质量靠只在"反复出现≥2"才改 ＋ 有界且可回滚 ＋ 持续进化自然收敛 ＋ Curator 维护。

取法：这不是二选一，而是"各取一半"——
· "分析该改什么" 学 SkillOpt：成败分桶找共性 ＋ 显式支持数（天然能做"出现≥2 次才改"的门槛）＋ 改动预算。
· "怎么安全改进 skill 目录" 学 Trace2Skill：多文件目录操作 ＋ 无冲突合并 ＋ 新建文件/链接成对 ＋ 目录健康复查（因为真实 skill 就是文件夹）。
· "验证" 谁都不照搬，也不重建：对齐 Hermes（成熟在线方案不测效果）——入口 ≥2 门槛 ＋ 每改可逆（快照/archive/provenance）＋ 持续进化自然收敛 ＋ Curator 维护。
· 重型编排（大批并行 map-reduce / 层级合并）都不要：线上是单个 skill、小批、增量、可回滚地慢慢来。
论文一句旁证：Trace2Skill 实测 +Combined 最稳、+Error 最可靠、+Success 最不稳（能 +17.6pp 也能掉到基线下）——所以"用成功经验，但靠『反复出现才采纳』强过滤"是对的。这正支持我们"成功侧保留但弱化、失败优先"的设计。
